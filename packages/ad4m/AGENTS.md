# AD4M SDK, mention waker and wake text (`packages/ad4m/`)

**SDK API changes to know (0.13.1-staging):** events go through one `client.on(<event>, handler)` (`agent-status-changed`, `agent-updated`, `apps-changed`, `notification-triggered`, …; there is no direct-message event); `PerspectiveProxy.addSubjectClass` is gone, use `addSdna(name, '', 'subject_class', shaclJson)`. Packages that declare their own narrow interface over the SDK (`tasks/src/ad4m-perspective.ts`) type-check against that interface, not the SDK, so a removed method only fails at run time: run `ad4m.integration.test.ts` against a live executor after moving the pin.

**The mention waker** (`packages/ad4m/src/waker.ts`) runs the SDK's `WakerSubscriptionManager` with one subscription per watched perspective (every neighbourhood, plus `POST /api/ad4m/watch/perspectives`): two model queries over built-in abstract classes, opened by the manager under one id (`mentionSubscription`, the executor's `get_mention_waker_config` / `build_mention_query` / `build_mentioning_query` from ad4m #1587, built locally because the server talks RPC, not MCP; keep the two identical). `query` reads `ad4m://TextContent` `{ text }`: one `text contains` per term (names, then the DID), ORed, `properties: ["text"]`, `links: ["text"]`. `mentionQuery` reads `ad4m://Mentioning` `{ mentions }`: `mentions eq` the DID (WE's `we://mention` chip, or any relation a class aliases to `mentions` with `alias: { Mentioning: 'mentions' }`, text or not), `properties`/`links: ["mentions"]`. Both carry `author: { not: did }`, newest first, `limit` 50. The subscription carries `className`, `terms`, `did`, `mentionClass` and `mentionQuery`, and the SDK refuses a mention subscription missing any of them. A record both queries find wakes once, through the first to report it (`MentionMessage.via`, shown as `Matched by:`); a Mentioning row holds no text, so for those mentions the waker reads the text with one `ad4m://TextContent` model query by id (`textsOf`) before it emits the wake; a record with no text of its own (a text-less root) or a failed read leaves the wake without `body`. The manager wakes on a verified mention link to the DID whatever the text says, else only on a whole-word name or DID in a verified text link another agent wrote; it skips the agent's own links, resolves parents and ancestors through `ad4m://Container`, takes what a new subscription opens on as history, and persists a mention only once delivered (`ad4m-watched.json`, keyed `mention-<uuid>`; older uuid keys are migrated on load). Each mention emits `ad4m.perspective.mention` and `ad4m.thread.message` (item, the mentioning link's author, timestamp and signature verdict, parents, ancestors, body); the server injects the text (`By: <did> (signature verified)`) into the presence-internal thread. The wake carries only the text and its provenance (item, author with signature verdict, time, how matched, parents, ancestors): how to reply lives in the agent's stable prompt, never in each wake. The `presence_reply_ad4m` description states the mention rule (the wording of ad4m's waker prompts, coasys/ad4m#1889): a post for a person or a bot puts their DID in the item's `mentions` relation (the `we://mention` link that wakes them), plus a `marks` mention entry over the `@Name` where the class keeps marks. The executor does not derive mention links from marks (WE's client adds them itself), so an agent writing through `instance_create` sets both. A record whose only mention sits on a text-less root (a WE post whose text is in child blocks; a WE post comment, a `kind: reply` root hung off the post by `we://response`) wakes through Mentioning (wind-tunnel s10 cases 12 and R3). A WE reply is not a child: it hangs off what it answers through `we://response`, so a wake for one (s10 R1, R2) carries `Parents: (unknown)` (follow-up: resolve `we://response` holders as parents).

**Wake text is config (`ad4m.wake`, `packages/ad4m/src/wake-text.ts`, defaults in `@sovereign/core` `ad4m-wake.ts`).** The waker reads it at each wake, so a `PATCH /api/config` applies to the next wake with no restart. `template` holds the wake with `{body}`, `{address}`, `{author}`, `{verified}`, `{timestamp}`, `{via}`, `{parents}`, `{ancestors}`, `{context}`; an unknown name stays literal; a `[[...]]` segment drops out when a placeholder in it is empty; a line empty after rendering drops. `labels` hold the words for `{verified}`, `{via}` and unknown parents; `contextLine` (`{author} {time}: {text}`) formats one preceding message. The default template is today's text plus a `Before it:` block, and no pointer line: a call transcript arrives cut mid-sentence, and the block carries the messages around it, so the agent's prompt (`instance_transcript` on the Parents address) is the fallback only. `contextMessages` (default 5, 0 = off) is how many messages before the item, under its first parent, the wake carries: one TextContent query for the newest `N + 8` records under the parent (`order timestamp desc`, `properties: ["text","author","timestamp"]`, the executor's `instance_transcript` query; `where` compares numbers only, so there is no "before this timestamp" filter), then the N after the item in that list, oldest first, each clipped to 200 characters, the block capped at 1,200 characters. A mention outside the newest `N + 8` records, or a failed read, leaves the wake without the block, as `textsOf` does. Measured read-only on the live Coasys call channel: the query takes about 0.46 s up to 16 rows and 1.7 s at 30 rows, so a wake costs about 0.5 s more and about 150 tokens; a 30-message pull costs a model round trip, 1.7 s and about 1,000 tokens of transcript text (about 2,700 chars of speech plus author and time per line).
