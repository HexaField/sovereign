# PR watch (`packages/server/src/pr-watch/`)

MCP tools `pr_watch` / `pr_watch_list` / `pr_unwatch` (they replaced `ci_watch` / `ci_watch_list` / `ci_unwatch`; no aliases) let a thread watch a GitHub PR, or the checks of a branch or commit. The server polls; the thread gets messages (cron envelopes `[Cron: CI <target> @ <time>]` and `[Cron: PR <target> @ <time>]`) through the chat queue, so they never interrupt a turn. The tool description tells agents: after pushing a PR, call `pr_watch` with `events: ['ci','comments','reviews']` and end the turn; no crons for reviews or CI.

- **Events** (`events`, default `['ci']`: a bare call is the old CI watch):
  - `ci`: one message when the checks go red or settle green (below).
  - `comments`: new issue comments (`/issues/{n}/comments?since=`) and inline review comments (`/pulls/{n}/comments?since=`).
  - `reviews`: newly submitted reviews (`/pulls/{n}/reviews`; PENDING skipped) with state and body. Reviews already on the PR when the watch starts are history.
  - `state`: merged, closed, reopened, turned draft or ready (read from `/pulls/{n}`).
  - `comments`, `reviews` and `state` need a PR target: a branch or sha with any of them is refused (tool and service), and so is a PR already merged or closed.
- **CI sources:** check runs (GitHub Actions and Apps) and commit statuses (CircleCI on coasys repos posts statuses only), one state per name, check runs first.
- **CI result:** red: the first poll that sees a failed check. Green: every watched check finished, and still so on the next poll (`settleMs`, 10 s). CircleCI posts a job's dependants about a second after the job passes, so one all-finished poll can be partial. No check within 20 min of the watch's start, or of a re-arm (`noChecksTimeoutMs`), reports that instead.
- **CI in a longer watch:** CI is reported once per head commit. A CI-only watch ends with that message. A watch that also follows comments, reviews or state lives on (the CI message says what it still watches); with `follow` (default) a push re-arms CI for the new head, without `follow` CI stays done. A `ci` watch still waiting on CI shows as "Waiting for CI" in the Forge.
- **Batching:** comments, reviews and state changes collect into ONE message (`[Cron: PR …]`: the PR's `repo#n`, title and link, then one numbered entry per event: kind, author, time, `file:line` for an inline comment, the body cut to ~1,500 chars, a link). It goes out once nothing new arrived for 60 s (`quietMs`) or 5 min after its first event (`batchCapMs`), so a reviewer's burst of inline comments arrives together. CI messages stay separate. The waiting batch persists with the watch, so a restart does not lose it.
- **Trust (hard rule):** the thread's membrane (threads registry) picks its `forge.trustedAuthors` list (`trustedAuthorsOf`, read live). Only listed authors' text enters a message or the watch file; anyone else's entry is only `<kind> by <login> (untrusted), not read`, decided when the event is read. An untrusted PR author's title is left out of the header. No list configured: everyone passes. The watcher's own login is not trusted implicitly: put it on the list.
- **Own login:** the watcher reads its GitHub login once (`GET /user`, same client). Issue comments and inline comments by that login are ignored: they are the agents' own replies, and waking on them would loop. Reviews submitted from that login ARE delivered (the user reviews from it), with their top-level inline comments; a COMMENTED review with no body and only reply comments (GitHub wraps every inline reply in one) is skipped.
- **Lifetime:** a ci-only watch ends with its CI message, or after `timeoutMinutes` (default 720, max 2880). A watch with comments, reviews or state lives until the PR merges or closes (always reported, with any waiting batch, in its last message), its timeout (default 7 days, max 14), or `pr_unwatch`. Ten failed polls in a row end any watch with a message.
- **Cadence:** one loop every 10 s polls every watch in parallel (`PR_POLL.pollMs`); only a watch whose polls fail backs off (20 s doubling to 5 min). Requests carry the last ETag; unchanged answers are 304s, which do not count against the rate limit. Comment reads keep their `since` cursor (whole seconds, plus the ids seen at it) until something new arrives, so the URL and its ETag stay stable and a quiet PR answers 304; reviews read the last page the same way. Token from `gh auth token`, so any repo the `gh` account can read works (public coasys repos included); no webhook needed.
- **Follow:** a PR or branch watch moves to the new head after a push (default); `follow: false` stays on the commit.
- **Persistence and migration:** watches (with cursors, seen ids and the waiting batch) persist in `<dataDir>/pr-watch/watches.json` and resume after a restart. At startup, the old `<dataDir>/ci-watch/watches.json` is read once (when no pr-watch file exists yet), its watches become CI-only PR watches (`events: ['ci']`), and the old file is renamed `watches.json.migrated`.
- **Bus:** `pr.watch.ci` when a longer watch reports CI, `pr.watch.ended` once a watch's last message is delivered (both `{ threadId, repo, target, result, sha?, failed?, message?, url, events }`, `result` one of passed, failed, no-checks, timed-out, error, merged, closed); the timeline maps both. An unwatch emits nothing.
- **Shared fold:** `toCheckStates` lives in `@sovereign/forges` (`checks.ts`), so PR watch and the forge adapter's `checks()` agree on what failed. PR watch keeps its own polling: it needs each check's conclusion, URL and summary for its message, and per-watch ETags and head-following, which `Forge.checks()` (a summary) does not carry.
- **Tests:** `pr-watch/service.test.ts` (CI behaviour ported unchanged, batching and the cap, trust, own login, `since` + ETags, merge and close, refusals, restart, migration), `mcp-server.test.ts` (schema, validation, description), wind-tunnel s35 (the tools offered, no `ci_*`, a call reaching the watcher).
